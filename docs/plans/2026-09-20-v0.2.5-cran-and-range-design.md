# cncleanr 0.2.5 CRAN and range design

## Goal

Prepare a reproducible CRAN candidate without expanding the accepted syntax.
The release should correct metadata, exercise PDF manual generation in CI,
make submission comments concise, and improve range parsing performance while
preserving every documented result and problem reason.

## Options considered

1. Keep the current range loop and only cache repeated strings. This is the
   smallest change, but distinct ranges would remain slow.
2. Batch quantities and range endpoints in R, while deduplicating normalized
   input. This keeps the parser dependency-free, preserves its explicit rules,
   and removes repeated parser setup work. This is the selected approach.
3. Rewrite range parsing in C or as a new state machine. This could be faster,
   but adds substantial maintenance and compatibility risk without evidence
   that native code is needed.

## Range data flow

Character input is normalized once. Invalid digit spacing is detected before
whitespace removal so that `1 2` cannot silently become `12` in the quantity or
range parser. Non-missing, valid-spacing strings are deduplicated. The unique
values are passed to `parse_cn_quantity()` in one batch; exact values and open
bounds are mapped directly to range rows.

Values that are not quantities are scanned for candidate separators. Candidate
endpoint pairs from every input are flattened and passed to
`parse_cn_number()` once. A candidate is valid only when both endpoints parse
and neither endpoint is missing. This prevents missing markers such as `3-NA`
from reaching a comparison and raising an unstructured base-R error. Results
and problem reasons are expanded back to every original index after parsing.

## Metadata and release policy

Version 0.2.5 will add the copyright-holder role, declare English and Chinese
documentation, include a GitHub-recognizable MIT license file, and show both
CRAN and GitHub installation paths. The existing v0.2.4 tag remains immutable.
The CRAN comments will report only clean remote checks and the unavoidable new
submission note.

One Ubuntu release CI job will install TinyTeX and run the full manual check.
The other matrix jobs will retain `--no-manual` to avoid multiplying a costly
LaTeX installation across all platforms.

## Verification

Regression tests cover invalid spacing in all parsers, missing range endpoints,
factor and empty inputs, custom missing markers, duplicate inputs, and existing
problem schemas. Verification includes the dependency-free suite, testthat,
source build, CRAN-style check, a before/after range benchmark, spelling, and
the full GitHub Actions matrix.
